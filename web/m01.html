01

Signs of complexity

Chapter 1 of Saltzer and Kaashoek argues that the main enemy of a system designer is complexity, and that it rarely arrives all at once. A dashboard starts as one script. Then a second data source arrives, a new disease, a district that reports late, a second analyst. Nothing was designed badly; it simply grew.

The book gives symptoms you can check for in your own code:

  • Many components and many interconnections between them.
  • Irregularities: special cases such as "district X reports on Tuesdays" or "this clinic sends totals, not counts".
  • No short description: you cannot explain what the system does in a paragraph.
  • A large team, or too many people with partial understanding.

The first symptom is the one that bites fastest. Components grow one at a time, but the ways they can affect each other grow much faster. Add components below and count the possible interconnections when anything may talk to anything.

03
Propagation of effects

      
Here is SurveilLite version 0, the lab's dashboard_v0.py, running in your browser. One function, build_page(), loads the CSV, finds the latest week, sums the last four weeks, computes incidence, decides on alerts and lays out the page. It works, and it flags the Coastal cholera outbreak.

      
Three jobs in it know the date format: finding the latest week, filtering the last four weeks, and printing the date in the header and footer. The last line of the cell sends the same reports with dates written day first, 23/03/2026, as clinics in one region now do. Before you run it, decide which line fails first.

      

        

      

      
The page printed, then the day-first upload crashed on the very first parse, while finding the latest week. That is the lucky case: a crash is visible. Fix that line alone and the second parse crashes next. Change the format to 2026/03/23 instead and you get the same ValueError. A format that happened to parse but meant something different, such as month and day swapped, would not crash at all: it would quietly pick the wrong four weeks. The browser uses small stand-ins for csv and datetime, which Skulpt lacks; the lab uses the real modules and fails in the same places.

04
Modularity, abstraction, layering, hierarchy

      
The rest of the book elaborates four techniques for keeping growth under control. You will use all of them in this course.

      

        
TechniqueMeaningIn SurveilLite

        
          
Modularitysplit the system into parts that interact only through defined interfacesload, compute and present as separate functions

          
Abstractionhide how a module works behind what it doescall compute_incidence() without knowing it uses pandas

          
Layeringbuild each layer only on the one below itHTML on incidence tables on parsed reports on CSV

          
Hierarchygroup modules into larger modulesclinic, district, region, nation

        
      

      
Hierarchy is the one you already use as an epidemiologist. Nobody reads 40 clinic reports at once: you read 2 regions, then the 4 districts of the region that looks odd, then that district's 5 clinics. Each level stays small enough to understand. Roll up the last four weeks of cholera, one level at a time.

Modularity is the technique that fixes version 0. The lab splits build_page() into load_reports(), compute_incidence() and render_page(). The test for the split is strict: the modular version must print exactly the same page. That is what lets you refactor with confidence. The book adds a fifth habit, design for iteration: you will not get the design right first time, so make it cheap to change. Modularity is what buys you that.

05
Incommensurate scaling

      
A report is a duplicate if an earlier report has the same clinic, week and disease: a clinic pressed "send" twice. The lab's scaling.py finds duplicates two ways. The naive check compares every report with every other report. The set-based check remembers each key it has seen. Count the naive comparisons as the input doubles, and predict the ratio.

      

        

        

      

      
Each doubling of the input makes the naive check about 4 times slower and the set check only 2 times. 06
Trade-offs and design for iteration

      
The fourth source of complexity is the one you cannot remove. Every design choice gives something up. The set-based duplicate check trades memory for time: it keeps every key it has seen. The modular dashboard trades a little indirection for changes that land in one place. Refreshing the incidence table every minute keeps it current but loads the database; refreshing nightly is cheap but stale.

      
Because you cannot see every trade-off in advance, the book's advice is to design for iteration: expect to change the design, and make change cheap. Look back at the hero. Version 0 is not wrong; it is expensive to change, because every request reopens the one function that does everything. The modular version is not finished either; the "4 weeks" in the page header still has to follow the window by hand. Iteration is how you find those leftovers.

      

        
Version 0
Cheap to write, costly to change
One function, 19 lines. Every request means re-reading all of it, and a slip in the HTML can break the alert rule.

        
Modular
A little more code, changes land in one place
Three functions with narrow interfaces. A new date format touches load_reports(); a new alert rule touches compute_incidence(); a redesign touches render_page().
