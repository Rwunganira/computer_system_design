01

The naming model

Systems use names everywhere: variable names, file paths, URLs, patient IDs, district codes. Saltzer and Kaashoek describe all of them with one small model.

TermMeaningIn a Python dict
Name and valuea string used to refer to something, and the thing it refers toa key, and what is stored under it
Bindingan association between a name and a value; binding a name is the act of making it mean somethingd[name] = value
Unbindingremoving that meaningdel d[name]
Contexta set of bindings; a name only has a value in some contextthe dict itself
Resolutiontaking a name and a context and returning the value, or failingd[name], which may raise KeyError

That is why every context in this module is a dict. A naming scheme is the set of rules that says which names exist, which values they can refer to, and how to resolve them. Here is Clinic A's context, in miniature.


      

      

    


    
    

      
02
Context matters: path names

      
Clinic A calls a child "P-0042". So does Clinic B, about a different child. Neither is wrong: each local ID is bound in its own clinic's context. Problems start when a name escapes its context. A report that says only "P-0042", with no clinic attached, cannot be resolved.

      
The fix is to say which context to use. A path name like clinic_a/P-0042 names the context first and the patient second. Resolving it is a loop: look up clinic_a in the root context, get a context back, look up P-0042 in that. Each lookup's value is the context for the next component. Step through it.

03
Absolute and relative names

      
An absolute name is resolved from a fixed, well-known root, so it means the same thing wherever it is used. A relative name is resolved from a working context, the place you are standing. Inside Clinic C's own software, "P-0042" alone works fine, because the working context is Clinic C. The same string in a national report is ambiguous, because the report has no working context.

      

        
Absolute
clinic_c/P-0042
Starts at the root. Safe to copy into an email, a CSV export or a national report.

        
Relative
P-0042
Means a child only inside one clinic. Correct at the clinic's desk, unresolvable once it leaves.

      

      

        

        

      

      
An unbound name raises an error rather than returning something plausible. That is the same choice the case-definition parser made in Module 2: fail loudly at the edge rather than quietly in the middle of a report.

      

    


    
    

      
04
Pure and overloaded names

      
A pure name carries no information beyond identity: P000042 tells you nothing about the child. An overloaded name packs other meaning into the name: a district code inside a patient ID, or "name plus date of birth" used as the key. Overloading is tempting because the name is readable and you can check it against the person in front of you. It fails in two ways:

      
    
        
  • Two different things share the name. Two children called Paul Uwimana, both born on 2022-04-03, get the same key. A dict keyed that way silently keeps one, and their vaccination histories merge.
    • 
        
  • The meaning changes but the name cannot. A patient ID that embeds the district becomes wrong when the family moves. A pure ID stays right.
    • 
      

      
How likely is the first failure? The synthetic population draws from 16 given names, 12 family names and about five years of birth dates: 16 × 12 × 1,825 = 350,400 possible keys, far more than 2,000 children. Move the slider and see.

05
URLs are names too: two districts called Central

      
The same problem appears at the top of the system. SurveilLite's eight districts include two named "Central", one in the North region (N-CEN, 182,000 people) and one in the South (S-CEN, 205,000). A URL like /districts/Central/cases is a name. The lab's Flask app maps it through a {district_name: district_id} dict, which quietly binds "Central" to whichever row came last.

      

        

        

      

      
Nothing crashes. GET /districts/Central/cases returns South Central's 1,074 cases, and North Central, 182,000 people and 892 cases, has no URL at all. The dashboard is just wrong. Clinic names collide too: both districts have a "Central Health Centre 1". Try URLs against the naive resolver and against the fixed one you are about to write.

The fix has three parts, and none of them breaks a URL that already worked. Accept the unambiguous district_id as a name. Let the caller qualify a name by region: /regions/North/districts/Central/cases. And when a name is still ambiguous, answer 300 Multiple Choices with the unambiguous URLs, instead of a guess. A guess is wrong some of the time and nothing tells the user.

06
Indirection and aliases

      
An old saying, usually credited to David Wheeler, goes: "any problem in computer science can be solved by another level of indirection." The book's version is to let a name be bound to another name rather than directly to the thing. Clinics bind their local IDs to registry IDs; only the registry binds registry IDs to records. Compare the two designs as a child moves clinic and then has a mistyped birth date corrected.

With indirection, a child who moves gets a new local name bound to the same registry ID, so their history stays whole; a corrected birth date is fixed once, in the registry, and every name that leads there sees it. The cost is an extra lookup, and one new failure mode.

      
That failure shows up with aliases. Old reports name clinics by the name they had at the time. When a clinic is renamed, its old name becomes an alias: a name bound to a newer name, not to the clinic. "Lakeshore Health Centre 2" was renamed "Lakeshore Mother and Child Clinic", then "Lakeshore District Hospital"; last year's report still has to resolve to clinic C17, two hops away. And if someone ever binds an alias back to an older name, the chain becomes a loop that a naive resolver follows forever.

      

        
You tryExercise 2 of the lab.

        
Write resolve_clinic: follow aliases until you reach a current name and return its clinic ID. Raise LookupError for a name bound in neither context, and also when following aliases takes more than max_hops steps. Then write rename_clinic: move the clinic ID to the new name, remove the old binding, and add the alias old to new. Raise LookupError if old is not a current name and ValueError if new is already in use.
