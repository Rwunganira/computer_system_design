01

One computer, many virtual ones

Module 4 enforced modularity by putting the client and the service in separate programs that talk only by messages. A real computer for every module would be expensive. Virtualization gives each module the illusion of its own computer while they share one physical machine. The book virtualizes the three fundamental abstractions from Chapter 2:

Real thingVirtual versionWhat it gives each module
processor (interpreter)threadits own processor, which the scheduler shares out
memoryvirtual memory (address spaces)its own memory, which others cannot touch
communication linkbounded bufferits own message channel to another module
Process

A thread plus its own address space

Two processes cannot corrupt each other's memory, so the modularity is enforced. Sharing data means sending messages.

Threads in one process

Many threads, one address space

Cheap and convenient: they all see the same variables. All the protection is gone, and coordination is your job.

This module stays inside one process, the risky case. The SurveilLite lab pipeline has producer threads reading four labs' result files and consumer threads validating results and counting positives, all sharing one counter.

02

Threads as interleavings

The lab uses Python's threading module, which the browser's Python does not have. We lose nothing by simulating it, and gain something: you see every choice the scheduler makes. A thread here is a generator. Each next() runs it to its next yield, one step. A schedule is the order in which the scheduler picks threads, written as a string like "ABABAB".

Counting a positive looks like one step, count += 1, but it is three: read the count into a local variable, add one, write it back. Predict what the interleaved schedule leaves in the counter.

03
Race conditions

      
A race condition is a bug where the result depends on the timing of the threads. It is wrong sometimes, which is worse than always. A surveillance count that is slightly low on some runs is the kind of error nobody notices until an outbreak is missed.

      
The lab's four result files hold 341 positives: 87, 98, 70 and 86. Here four consumer threads count them under a random scheduler. SWITCH = 0.5 plays the part of the lab's time.sleep(0) between read and write, which hands the processor away on purpose so the race shows up on every run. Will the counter ever report more than 341?

      

        

        

      

      
The lab's real threads lost 185 to 193 updates per run; this simulation loses a similar share. The error only ever goes down: a lost update overwrites someone else's increment, and nothing in read-add-write can add an extra one.

      
Now set SWITCH = 0.01, a scheduler that rarely switches mid-update, like a real one without the pause. Run it: one run loses 50 positives and two are exactly right. That is the dangerous version. Python's global interpreter lock does not save you either: it makes one bytecode run at a time, not your three steps.

      

    


    
    

      
04
Locks: before or after, never during

      
The fix is a lock. A thread acquires it before the read and releases it after the write; any other thread that wants it waits. Then the three steps of one update happen entirely before or entirely after another thread's, never interleaved. In the lab the whole fix is one line:

      
with self.lock:          # threading.Lock()
    current = self.value
    time.sleep(0)
    self.value = current + 1

      
The book builds locks from an atomic hardware instruction that tests and sets a memory cell in one indivisible step. Here try_acquire plays that instruction: the simulated scheduler never switches inside it. Turn the lock on in the animation at the top and try to make Thread B slip in. Chapter 9 returns to before-or-after atomicity in depth.

05
The bounded buffer

      
A lock keeps threads from interfering. Threads also need to wait for each other: a consumer cannot validate a result that no producer has delivered yet. The book calls this sequence coordination. Lab files arrive faster than consumers can validate them, or slower, so producers and consumers share a buffer that holds at most N results, a bounded buffer, with two rules:

      
    
        
  • a producer that finds the buffer full must wait until a consumer takes something;
    • 
        
  • a consumer that finds it empty must wait until a producer adds something.
    •

06
Wait and notify: while, not if

      
Waiting by spinning in a loop wastes the processor. Instead, a real thread waits on a condition variable, which releases the lock while it sleeps, and the other side notifies it when the state changes. The lab's BoundedBuffer uses one lock and two condition variables, not_full for producers and not_empty for consumers. Python's queue.Queue is built exactly the same way: use it in real code, and build it once by hand so you know what it does.

      
Being notified means "the state changed", not "the state is now what you need". Between the notify and the moment the woken thread gets the lock back, another thread can get there first. Step through both versions.

07
Processes: no sharing by accident

      
The lab's last exercise replaces threads with processes, using ProcessPoolExecutor. Each process has its own address space, the virtual memory row of the table in section 1. A counter created in the parent is copied into each child; the children increment their copies, and the parent's stays at 0. Results must travel back as messages, here return values, much like the client and service in Module 4. The browser has no processes, so the cell copies the parent's memory by hand. Predict the last line.

      

        

        

      

      
Nothing is shared, so there is nothing to race on and no lock is needed. Sharing on purpose needs multiprocessing.Value or a Manager, which brings locks back.
