01

One action, two writes

VaxRecords keeps each child's vaccination history in one file and each clinic's vaccine stock in another. Recording a dose appends to the history and decrements the stock. The rule that ties them together is an invariant, something that must be true whenever nobody is in the middle of an update:

for every clinic and vaccine: stock left + doses given = stock received

The naive recorder writes the history, then the stock. Here it is with the disk simulated as a dict and the power failure simulated as an exception raised before step 1. (The local lab writes real JSON files; Skulpt has no file system, so a dict stands in.) Predict whether the invariant still holds afterwards.


      

      
The history says two doses were given; the stock says only one left the fridge. Restarting does not help, because nothing on disk records that an action was half done. Coverage reports and stock reports now disagree, and someone will spend a week reconciling them by hand.

      
Two kinds of atomicity

      

        
Failures
All-or-nothing
A multi-step action either completes, or has no visible effect, despite crashes. This module's first half.

        
Concurrency
Before-or-after
Concurrent actions behave as if one ran completely before the other. Two nurses dispensing from one stock at once must not lose an update.

      

      
A database transaction gives you both at once, which is why it is such a useful abstraction.

      

    


    
    

      
02
The commit point and the shadow copy

      
Every fix needs a commit point: a single step that cannot be half done. Before it, a crash means the action never happened. After it, a crash means the action did happen and must be finished. The design question is always "what is my one indivisible step?"

      
The shadow copy answers it with a file rename. Put history and stock in one file, state.json. To record a dose, write a complete new version to state.json.tmp (the shadow), flush it to disk, then call os.replace to rename it over the old file. On POSIX and Windows that rename is atomic: afterwards the name points at the old file or the new one, never a mix. A crash leaves at worst a stray shadow, which start-up deletes. Pick Shadow copy in the machine at the top and drag the slider: every crash point recovers to a consistent state.

      

        
Strength
Simple and robust
Recovery is one line: delete a leftover shadow. There is no log to read and nothing to redo.

        
Cost
Rewrite everything
Every dose rewrites the whole file. Fine for one clinic; far too slow for a national register.

03
A write-ahead log and a recovery procedure

      
The second fix keeps the two files and adds an append-only log. To record a dose:

      
    
        
  1. Append the intended changes to the log: "add dose 2 to the history", "set the stock to 18".
    2. 
        
  2. Append a COMMIT record. This is the commit point.
    3. 
        
  3. Only now install the changes in the real files.
    4. 
        
  4. Append an END record: the installs are done.
    5. 
      

      
The write-ahead rule is "log before you install". After a crash, a recovery procedure runs on start-up and reads the log. A transaction with COMMIT but no END is redone. A transaction without COMMIT is ignored: by the write-ahead rule, nothing of it was installed. Pick Write-ahead log at the top and drag the slider to "before install stock": the files on disk are inconsistent right after the crash, and consistent after recovery.

      
Recovery can itself crash and run again. So redo must be idempotent: running it twice must have the same effect as once. Try both ways of logging the stock change below.

"Set the stock to 18" can be redone any number of times. "Subtract 1" takes another dose off the books every time recovery repeats, and if the crash came after the stock was installed, even the first redo is one too many. Logs record new values, not differences.

04
Let the database do it

      
The third fix is the one to use in real work: put both writes inside one database transaction. SQLite keeps its own journal and runs its own recovery every time it opens the file. Everything between BEGIN and COMMIT is all-or-nothing, and the lock that BEGIN IMMEDIATE takes also gives before-or-after atomicity between concurrent writers. Shadow copies and logs are how that works inside.

      
The local lab's sqlite_txn.py kills a real child process with os._exit between the INSERT into history and the UPDATE of stock, which skips every except, finally and ROLLBACK, as close to pulling the plug as Python gets. It then reopens the database. Here is what it prints (SQLite does not run in the browser):

05
Before-or-after: lost updates and locks

      
Now the other kind of atomicity. Two nurses at clinic C05 give an OPV1 dose at the same moment. Each one's request does a read-modify-write on the shared stock: read the number left, subtract one, write it back. Step through it with and without a lock.

Without the lock, both nurses read 20 before either wrote, so one write overwrote the other: a lost update. Two doses were given and the stock fell by one. The fix is to make the read and the write one indivisible step with respect to other workers, by holding a lock across both.

      
Skulpt has no threading, so the cell below simulates the two requests as generators: each yield is a point where the scheduler may switch to the other nurse. (The local lab uses real threads and a threading.Barrier to force the same interleaving.) Predict the final stock.

      

        

        

      

      
In a Flask app with several worker processes, a Python lock is not enough: each process has its own. The lock has to live where the data lives, such as a database row lock, which is what BEGIN IMMEDIATE takes in SQLite.

      

    


    
    

      
06
Across two services: two-phase commit

      
Suppose history and stock belong to two separate services, each with its own storage. No single rename or local transaction covers both. Two-phase commit stretches the commit point across them with a coordinator:

      
    
        
  1. Phase 1, prepare. The coordinator asks each participant whether it can do its part. A participant that can records its tentative change durably and votes yes. A yes is a promise: "I can commit this even if I crash."
    2. 
        
  2. Commit point. The coordinator writes its decision to its own log: commit only if every participant voted yes.
    3. 
        
  3. Phase 2. The coordinator tells every participant the outcome, and each commits or aborts.
    4. 
      

      

        
Worked example
          

        

        
        

        

        

      

      
The crash scenario shows the price. Once both participants are prepared, they have given up the right to abort on their own, and they cannot learn the outcome without the coordinator. They are blocked, holding the reserved dose, until the coordinator restarts and resends its logged decision. During that time VaxRecords cannot show the dose to a nurse, and the stock service cannot give the reserved dose to another child.

Return "commit" or "abort". participant_on_silence(status) runs when a participant has heard nothing for a long time; status is None (has not voted), "prepared", "committed" or "aborted". Return "abort" if it may safely abort on its own, "wait" if it must keep asking the coordinator, or "nothing" if the transaction is already finished for it.
