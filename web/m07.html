The network only tries. Getting it right is the endpoints' job.

01

Three layers, and a deliberately weak promise

The book organises a network into three layers, each built only on the one below. The surprise is how little the middle one promises. Tap each layer.

Worked exampleA clinic's text, layer by layer.

The network layer's promise is best effort: it tries to deliver each packet, with no guarantee that it arrives once, in order, or at all. A packet may be lost (a queue overflowed), duplicated (a link resent it), delayed and reordered (it took another path), or, rarely, damaged. SMS behaves the same way, which makes it a good stand-in: two texts sent a minute apart can arrive in either order.


      

      
The network layer is weak on purpose. Every application wants something different: a weekly report must arrive, a live video call prefers a late frame dropped. So the network does the common minimum, and the end-to-end layer in the two endpoints turns best effort into whatever the application needs.

      

    


    
    

      
02
Fire and forget gets it wrong both ways

      
The simplest protocol: each report is sent once, and the office adds up whatever arrives. Lost texts make totals too low; duplicated texts make them too high. For surveillance both are dangerous: a missed cholera report hides an outbreak, a doubled one raises a false alarm.

      
The browser has no SMS gateway, so SmsChannel simulates one with seeded random choices, as the lab does. To keep the browser quick, each message here carries one district's weekly total (8 senders, 96 reports) instead of one clinic's (40 senders, 480 reports); the true district totals are the lab's. Before you run it, decide: will each district be too low, too high, or could it be either?

03
Sequence numbers, ACKs and timeouts

      
To recover lost reports the clinic needs to know what arrived. Three mechanisms work together:

      
    
        
  • Sequence numbers. Each clinic numbers its reports 1, 2, 3, so a report can be named.
    • 
        
  • Acknowledgements. The office replies ACK 7 when report 7 arrives.
    • 
        
  • Timeouts and retransmission. A clinic that gets no ACK within a timeout sends the report again.

04
Duplicate suppression: count each report once

      
The office remembers which (clinic, sequence number) pairs it has already counted. Every copy is acknowledged, because the clinic needs to hear back (the first ACK may have been lost), but each pair is counted only once. That is at-most-once. Together with at-least-once from the previous section, each report is counted exactly once, and the totals are correct.

      

        

        

      

      
Reordering costs nothing here: report 8 arrived before report 7 and the total does not care, because addition does not care about order. A protocol that needed order, say "dose 2" must be recorded after "dose 1", would hold back early arrivals until the gap fills. VaxRecords has exactly that problem with dose records synced from tablets, and a resent "dose given" must never record a second dose.

05
Choosing the timeout, and what reliability costs

      
The timeout is a trade-off. Too short, and clinics resend reports that were merely slow, wasting texts and money; the office drops the extra copies, so totals stay right, but someone pays. Too long, and a lost report sits unnoticed before anyone resends it. Here a round trip takes 2 to 6 rounds, because each direction is delayed 1 to 3 rounds.

Even with a sensible timeout, loss costs texts. A report is finished only when the report and its ACK both survive, which happens with probability (1 − p)², so you expect about 1 / (1 − p)² sends per report. Check that with a quick simulation.

      

        

        

      

      
This plot is drawn by pylab, a browser subset whose plot, title and legend calls behave like matplotlib's. At 10% loss reliability costs about 1.2 texts per report, at 30% about 2, at 50% about 4. The lab measures slightly less, because a channel duplicate is a free second chance.

      

    


    
    

      
06
Damaged messages: detect, then let retransmission correct

      
Rarely, a text arrives changed: one digit flipped. The protocol so far would happily count 13 as 18. The fix reuses everything already built. The sender appends a checksum, a short value computed from the text. The office recomputes it; if it does not match, the office drops the message without an ACK, and the sender's timeout resends it. Detection plus retransmission equals correction.

      
The lab uses zlib.crc32. The browser has no zlib, so the cells below use a polynomial rolling hash, a stand-in that also catches every single changed character. A checksum must be chosen with care, as this predict cell shows.

07
The end-to-end argument

      
Where should "make sure the counts are right" live? The SMS gateway already checks that each text arrived intact. But it cannot know that a nurse keyed 14 instead of 41, that the office's database dropped a row, or that a bug further along lost a report. Only the application at the endpoints knows what a correct count is.

      
The end-to-end argument: a function that needs the application's knowledge to be done correctly can be implemented correctly only at the endpoints. A lower layer can help, but cannot finish the job.

      
So the end-to-end check is needed anyway. A check in a lower layer is then justified only as a performance improvement (catching errors earlier, fewer end-to-end retries), never as a replacement. That is why the checksum in section 6 lives in the clinic and the office, not in the gateway.

      

        
Gateway check
Each text arrived intact
Useful: it saves resends. But it is blind to a wrong number keyed in, a row the database lost, or a report never sent.

        
End-to-end check
The totals add up
Each clinic also sends a monthly summary of the cases it reported. The office compares it with what it received. This catches every failure in between.
