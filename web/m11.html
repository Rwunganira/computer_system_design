01

Security is a negative goal

Most of this course has asked "does the system do X?". Security asks "can anyone make the system do something it should not, ever?". That is much harder. A test shows that one attack fails; it cannot show that every attack, by every adversary, fails. So the book leans on a few design principles and a simple structure small enough to check.

02

The guard model

Every request to a protected resource passes a guard that does three things, in order:

  1. Authenticate: who is asking? VaxRecords checks a password once, then issues a random token for later requests.
  2. Authorize: may this principal do this to this object?
  3. Audit: record who asked for what, and the answer, in a log the people being audited cannot rewrite.

The first version of VaxRecords, vax_api_insecure.py, has a login, tokens and a 401 for strangers, so it feels secure. But its access check is logged_in_is_enough, which always returns True. Amina, a North-Central district officer, can change the ID in /patients/<id> and read any child in the country. This bug has a name, an insecure direct object reference (IDOR), and it is one of the most common real web bugs.

The real lab runs both versions as Flask servers and attacks them with requests. Here the server is a function and the network is a function call, with the same 30 synthetic children. Amina tries P000001 to P000030. About one child in five lives in North-Central. Predict the last line.


      

      
Authentication worked perfectly: a request without a valid token gets 401. The leak is entirely in the second step. An audit log would not have stopped it either; it only makes the misuse discoverable, which also deters it.

      

    


    
    

      
03
Authorization: check every read

      
The fix is complete mediation: compare the record's district with the user's on every read, not once at login. The secure version puts that decision in one small function, can_read, so a reviewer can see all of it at a glance (economy of mechanism), and makes anything it does not explicitly allow a denial (fail-safe defaults).

04
Authentication: salt and a slow hash

      
The insecure version stores passwords in plain text, another flaw. The secure version never stores a password at all. For each user it keeps a random salt and a slow hash of salt plus password (hashlib.scrypt in the lab). At login it hashes what the user typed with the same salt and compares. If the user table leaks, the salt stops one precomputed table from cracking everyone at once, and the slowness makes every single guess expensive.

      
hashlib is not available in the browser, so the cells on this page use h64, a small hand-written 64-bit hash, as a stand-in for SHA-256. It shows the shape of the idea: same input, same output; change one character and the output changes completely. It is not secure, and the real lab uses the real library.

      

        
Worked exampleThe user table has leaked. What does the attacker see?

        

        

        

      

      
Two clinic nurses, Grace and Paul, chose the same weak password. Under a plain hash their stored values are identical, which tells the attacker they share a password before any cracking starts. Predict what the salted version prints.

      

        

        

      

      
Slowness is a feature at login, where one person waits a fraction of a second once. It becomes a problem if every request re-checked the password, or if an attacker floods the login endpoint to burn the server's CPU. That is why VaxRecords checks the password once and then issues a token.

      

    


    
    

      
05
Audit: a tamper-evident log

      
An audit log is only useful if the people being audited cannot rewrite it. Exercise 2 makes the log tamper-evident by chaining hashes: each entry stores the hash of the one before, and its own hash covers that previous hash plus its contents. Editing, deleting or reordering any entry breaks every link after it.

      
Try it. Edit any entry's text, delete one, or cut the last one off. Then play the attacker properly: rewrite every hash after your edit so the chain looks whole again. Only the head published elsewhere catches that.

06
MACs, replay and encryption

      
SurveilLite asks VaxRecords for coverage figures, machine to machine, with no password. Instead both services share a secret key, and SurveilLite signs each request with a message authentication code: a hash keyed with that secret (HMAC-SHA256 in the lab), over the method, path, timestamp and body. VaxRecords recomputes the MAC and compares. An altered body or a guessed key fails. The timestamp limits replay to a short window. Here the MAC is h64(key + h64(key + message)), the nested shape of HMAC, standing in for the real thing.

The comparison itself must not leak. A plain == on strings stops at the first differing character, so the time it takes tells an attacker how many leading characters of a forged signature were right. hmac.compare_digest always looks at every character. In production VaxRecords would run behind TLS, which provides both confidentiality and integrity on the wire; the lab runs on plain localhost HTTP to keep the code short. All users, passwords and keys in this module are synthetic test values. Real keys never belong in source code: load them from the environment or a secrets manager.
