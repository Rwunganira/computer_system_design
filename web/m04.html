01

Soft and enforced modularity

In Module 1 you split SurveilLite into load, compute and present modules. That is soft modularity: the modules are functions in one program, so the boundaries hold only as long as every module behaves. A function can write into another module's data, loop forever, or crash, and the whole program goes with it. If the dashboard and dose recording share a program, a bug in the chart code can stop health workers from recording doses.

Enforced modularity puts each module in its own program and lets them talk only by sending messages. The client sends a request; the service does the work and sends a reply. The client cannot touch the service's memory, and the service checks every request it receives. The book calls this the client/service organization, and almost every system you use is built this way.

Soft

One program, many functions

Fast, simple calls. One crash, infinite loop or stray write takes everything down.

Enforced

Separate programs, messages only

A failure stays inside the program that had it. Every call can now be slow, lost or repeated.

Remote procedure call

      
Writing every message by hand is tedious, so we wrap it in something that looks like a function. client.record_dose(dose) packs the arguments into a request, sends it, waits, and unpacks the reply. This is a remote procedure call (RPC), and the code that hides the messages is the stub. In the lab the stub is VaxClient, and requests plus Flask do the packing and unpacking. 03
A local call has two outcomes; a remote call has three

      
The danger of an RPC is that it looks like a local call but is not one. A local call runs once and then returns or raises. A remote call can also:

      
    
        
  • be slow, because the network or the service is busy;
    • 
        
  • get no reply at all, because the request was lost, the service crashed, or the reply was lost;
    • 
        
  • run twice, if the client sends it again.
    • 
      

      
The hard case is the lost reply. The client waits, gives up after a timeout, and cannot tell whether the dose was recorded. Try each failure below and compare what the client sees with what VaxRecords actually holds.

04
At-least-once and at-most-once

      
After a timeout the client must choose. It can give up, or it can send the request again. Each choice gives a different guarantee, which the book calls the call's semantics.

      

        
SemanticsWhat the client doesWhat can go wrong

        
          
At-most-oncesend once, never retrya lost request means a dose never recorded

          
At-least-onceretry until a reply arrivesa lost reply means the dose recorded twice

          
Exactly-onceretry, and the service suppresses duplicatesneeds the service to remember what it has done

        
      

      
The cell simulates the lab. In rpc_demo.py the service saves each dose and then loses 30% of its replies, drawn from a seeded generator. With seed 4 the same nine replies are lost on every run, and LOST below replays exactly that pattern: dose 1 loses two replies, dose 7 loses four. The real lab uses Flask and requests; here the network is a Python object that raises Timeout. The client retries up to five times, as the lab's does. Nineteen records for ten children: the register now says P000007 had five measles doses. Now set RETRIES = 0 and run again. That is at-most-once: the service records 10, but the client gives up on 5 doses that were in fact recorded, and would tell the nurse they failed.

      
At-least-once is fine for an idempotent request, one that has the same effect however many times it runs. "Set Amina's MCV1 date to 2 March" is idempotent; "add an MCV1 dose for Amina" is not. For VaxRecords a duplicate is not harmless: the register says a child had a second measles dose, coverage figures are inflated, and stock looks lower than it is.

      

    


    
    

      
05
Idempotency keys

      
The fix is to make a non-idempotent request idempotent. The client gives each dose a unique idempotency key (in the lab a UUID) and sends the same key with every retry of that dose. The service remembers the reply it sent for each key; when a retry arrives with a key it has seen, it replays that reply instead of recording again. Retrying gives at-least-once delivery, duplicate suppression gives at-most-once execution, and together they give the effect of exactly-once.

06
Checking keys on the service

      
The service's side of the bargain has three cases, and a fourth that protects it from a buggy client:

      
    
        
  • No key: record the dose and reply 201 Created.
    • 
        
  • A new key: record the dose, remember the reply under the key, reply 201.
    • 
        
  • A key seen before, same dose: record nothing; replay the first reply with 200 OK.
    • 
        
  • A key seen before, different dose: the client is reusing keys. Record nothing and reply 409 Conflict, so the bug is loud instead of silently dropping Juma's dose.
    • 
      

      
In the lab the check and the record happen while holding store.lock, because two retries of one dose can arrive at the same moment on two server threads. Module 5 shows what goes wrong without it. The browser runs one thing at a time, so the exercise leaves the lock out.

07
Retry gently, fail gracefully

      
Keys make retries safe. They do not make them free. When VaxRecords is overloaded, 40 clinics retrying every quarter second keep it overloaded. Exponential backoff waits longer after each failure (0.5 s, 1 s, 2 s, 4 s), so a struggling service gets room to recover. Drag the outage length and compare.

Write post_with_backoff. Call post(payload); if it raises Timeout, call sleep(base_delay) and try again, doubling the wait after each further failure. Make at most retries retries.
