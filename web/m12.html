01

Everything at once

Each module so far isolated one idea: retries in Module 4, duplicate suppression in Module 7, checksums in Module 8, all-or-nothing writes in Module 9, authorization in Module 11. Real systems need them together, and the hard part is that failures do not take turns. The week the network is bad is also the week a disk fails and someone tries something they should not.

The capstone puts SurveilLite's report intake behind one small service. Clinics send POST /reports; district officers ask GET /districts/<id>/incidence. Each accepted delivery is appended to an intake log as a new record, stored on two replicas, each with a checksum, written with write-then-rename so a crash never leaves half a file. Three decisions are left pluggable, because they are where the course's ideas live.

02

The naive parts, and where 459 comes from

NaiveParts is what a first version usually does: accept everything, trust the first copy, and let any logged-in user do anything. It is not a strawman. Each choice is the simplest thing that works on a good day, and on a good day you cannot tell it from a correct system.

The lab runs the week through Flask with hashlib and real files. Neither runs in the browser, so this page simulates the same service in plain Python: replicas are dicts, and the checksum is a small polynomial hash standing in for SHA-256. The true Coastal cholera total for the week is 40 + 25 + 31 + 44 = 140. Before you run it, work out what the naive dashboard shows.

03
accept: count each report once

      
Two things happened on the network side. C31's phone never heard back and sent the same report again, which is at-least-once delivery from Module 4. C32 came back online after three weeks and its reports arrived as sequence numbers 3, 1, 2, because a best-effort network promises nothing about order (Module 7). A correct intake must count every report exactly once, whichever order and however many times it arrives.

      
The fix is duplicate suppression with an idempotency key: each report names itself by (clinic, sequence number), and the service remembers the keys it has already accepted. That gives at-most-once on the server side; combined with the phone's retries, each report counts once. Deliver the week's messages one at a time and compare three policies.

It suppresses the retry, but it throws away weeks 1 and 2 from C32 because they arrived after week 3. Dropping real cases silently is as bad as doubling them. A set of keys has no notion of order, which is exactly what an offline clinic needs.

04
read_verified: a missing number beats a wrong one

      
On Thursday night a disk silently changed one stored report: replica 1 of C32 #2's record now says 310 cases instead of 31. In Module 8's words the fault is the flipped digit, the error is the wrong value sitting in replica 1, and the failure is the dashboard showing it. A checksum stored beside the data catches the error before it becomes a failure: recompute it on every read and compare.

      
Detection is only the first of three jobs. read_verified must also mask the error by returning a good copy, repair the bad replica so the redundancy is restored, and, if no copy is intact, fail fast by raising an error instead of guessing. Corrupt one replica or both, then read.


      

        
Worked example

        

        
Both replicas hold C32 #2 with 31 cases and a matching checksum.

      


      
The checksum is a short value computed from the whole payload, so changing any field changes it. Predict whether the stored sum still matches after the digit flips.

      

        

        

      

      
Why raise instead of returning whatever is there? In surveillance a confident wrong number drives real decisions: a team is sent, a district is flagged. A visible gap gets someone to fix the data. That is fail-fast, and it is the same reasoning as Module 8's argument for detecting before masking.

05
authorize: least privilege, denied by default

      
Two requests that week were made by real, logged-in users. A Hillview officer asked for Coastal's incidence, and a Coastal nurse submitted a report as clinic C01. Authentication worked both times: the service knew exactly who was asking. What was missing was authorization, the decision whether that principal may do that action.

      
Module 11's principles turn into three rules. Least privilege: a clinic may only submit for itself and an officer may only read their own district. Fail-safe defaults: anything not explicitly granted, including an unknown role or an anonymous user, is denied. Complete mediation: every request goes through authorize, reads included, and every decision, allowed or not, goes into the audit log. Switch the matrix between the two policies and tap any cell for the reason.

Where each check belongs

      

        
CheckWhy it lives at the endpointWhat a lower layer cannot do

        
          
acceptOnly the application knows that (clinic, sequence number) names one reportA reliable transport removes duplicates within one connection, not a retry the phone makes after a timeout on a new connection

          
read_verifiedThe check runs on the data that is about to be counted, after every layer that could damage itA disk's own error correction does not cover a bad write, a buggy copy or a file edited by hand

          
authorizeOnly the service knows which clinic belongs to which district and who may read whatEncryption and login prove who is asking, not what they may do

        
      

      

    


    
    

      
07
After the week: restarts and going further

      
The parts survive the scripted week, but seen lives in memory. When the service restarts, the set is empty, and a retry that arrives afterwards looks new. The intake log is append-only, so the late retry becomes a second record and is counted twice. Predict the total.

      

        

        

      

      
The fix is to keep seen in the same durable store as the reports. That raises Module 9's question: recording the key and storing the report must happen all-or-nothing, or a crash between the two either loses the report (key saved, report not) or lets a later retry count it twice (report saved, key not). In a database, both go in one transaction; with files, the report's file name can be its key, so writing the file and recording the key are the same atomic rename.

      
    
        
  • A tamper-evident audit log. Chain each entry to the previous entry's hash, as in Module 11's exercise, so an insider cannot quietly delete the record of a snoop.
    • 
        
  • A third replica and a voter. With two replicas and a checksum you can detect and repair; triple modular redundancy can outvote one bad copy even without a checksum. It costs a third write on every report. Worth it when a wrong value is very expensive and checksums cannot cover the fault, such as a bug that computes the wrong number and checksums it faithfully.
