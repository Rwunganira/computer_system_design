01

Three abstractions

Saltzer and Kaashoek argue that almost any computer system can be described with just three kinds of part. Each hides a great deal of mechanism behind a very small interface.

AbstractionInterfaceIn SurveilLite and VaxRecords
MemoryREAD(name), WRITE(name, value)a SQLite table, a CSV file, a Python dict, a dose record
Interpreteran instruction reference, a repertoire, an environmentthe CPU, the Python interpreter, Flask's request loop, a case-definition evaluator
Communication linkSEND(link, message), RECEIVE(link)HTTP between dashboard and API, an SMS from a rural clinic

The value of an abstraction is that you can swap what is behind it. A "memory" might be RAM, a disk, or a table on another continent; the code that calls READ should not have to care. It will care about speed and about failure, and that is what most of the book is about.

Memory remembers, interpreters act, links carry messages between places that share no memory. Name the part and you know which questions to ask about it.

02

Memory and read/write coherence

The simplest promise a memory makes is read/write coherence: a READ of a name returns the value of the most recent WRITE to that name. A Python dict keeps this promise, so it makes a perfectly good model of a memory. Here SurveilLite's weekly counts are stored under names like N-RIV/week1/measles.


      

      
With one user and one copy, coherence is easy. It gets hard in three situations, and the rest of the course keeps returning to them:

      
    
        
  • Two writers do read, modify, write without coordination. Every individual write is coherent, yet an update disappears. That is the next section.
    • 
        
  • There are several copies, such as a cache or a replica on an offline tablet. Now "most recent" needs a definition. Module 10 returns to this.
    • 
        
  • A write is not atomic. A write of a large record might stop half way through (Module 9).
    •

Each write did exactly what a memory promises. "The last write wins" is true of the memory and wrong for the epidemiologist, because the last write was based on a stale read. This is a lost update, and nothing crashed: the child simply has no record of DTP1.

      
The property we actually want is what the book calls before-or-after atomicity: one clinic's update should happen entirely before or entirely after the other's. A cheap way to get it is a version check. The store keeps a version number for each name; write_if(name, value, version) writes only if the version is still the one you read, and otherwise refuses so you can read again and retry. 04
Interpreters: fetch, decode, execute

      
An interpreter is a loop that never stops. It fetches the next instruction, decodes it to find out what kind of instruction it is, executes it, possibly changing its environment, and repeats. The book describes every interpreter with three parts:

      

        
PartA processorSurveilLite's case-definition interpreter

        
          
Instruction reference: where the next instruction isthe program counterthe node of the tree being evaluated, and the record being tested

          
Repertoire: the instructions it knowsadd, load, store, branchand, or, var, cmp

          
Environment: the state it acts onregisters and memorythe current patient record

        
      

      
Any time you write rules as data and a program that follows them, you have built an interpreter. Case definitions fit naturally. A WHO-style definition such as fever AND (rash OR cough) AND age < 15 changes when an outbreak investigation refines it. Hard-coded as a Python if, every change needs a developer and a deployment. As text that SurveilLite interprets, an epidemiologist can change it, and the system can store, compare and audit its versions.

      
The interpreter is built in three steps: tokenize the text, parse the tokens into a tree, and evaluate the tree against each record. The lab's tokenizer uses a regular expression; this one walks the characters by hand, which is itself a small fetch and decode loop. 05
Parsing: why AND binds tighter than OR

      
Tokens are a flat list. The interpreter needs a tree, so it knows what to combine with what. The parser follows a three-line grammar: a rule is and-groups joined by OR; an and-group is atoms joined by AND; an atom is a parenthesised rule, a comparison like age < 15, or a bare name like fever. Because OR sits at the top, AND groups first.

      
Each node of the tree is a tuple whose first item says what kind of node it is: ("and", left, right), ("or", left, right), ("var", name) or ("cmp", op, name, number). Evaluating the tree

      
The evaluator is the interpreter loop from the hero, written out. evaluate fetches a node, decodes its kind by looking at node[0], and executes the matching eval_ method. getattr(self, "eval_" + kind) is the decode step: it turns the string "and" into the method eval_and. Python's and and or stop early, so the interpreter skips any node whose answer cannot change the result. How many nodes does it execute for this record?

07
An interpreter that remembers, and links

      
Every instruction so far can be answered from the current record alone. Some cannot. Consider rash WITHIN 14 DAYS OF onset: true for a visit when the rash is present and the visit is 0 to 14 days after that patient's onset, the first visit the interpreter saw for them. The answer for one record depends on earlier records, so the interpreter must keep state between steps, as a processor keeps values in registers.

      
The lab parses the words WITHIN 14 DAYS OF onset into the node ("within", ("var", "rash"), 14, "onset") and uses real datetime.date values. Here the tree is written out for you and each visit carries a plain day number, so you can focus on the state. run calls the hook before_each before each record; that is where the interpreter gets to remember.

Communication links

      
The third abstraction moves messages between places that do not share memory: SEND(link, message) and RECEIVE(link). Unlike a memory, a link can lose, delay, duplicate and reorder what you give it. An SMS from a rural clinic can arrive twice, or after the next week's report, or never. This module only names the abstraction; Module 4 (clients and services) and Module 7 (networks) build on it.
